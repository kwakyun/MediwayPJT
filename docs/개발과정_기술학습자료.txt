실제 개발 과정에서 사용한 기술적 선택을 바탕으로 다음 내용을 학습하는 것이 목적이다.

- Python 프로젝트의 기능 분리 방법
- CSV 중심 데이터 파이프라인 구성 방법
- Streamlit의 재실행 구조, 상태와 캐시

- 규칙 기반 응답과 외부 AI의 계층형 결합

2. Python 프로젝트에서 UI와 계산을 분리하는 이유
======================================================================

초기 데이터 앱은 입력 위젯, 계산, 데이터 조회와 화면 출력이 하나의 파일에 섞이기 쉽다.
이 구조는 화면을 수정할 때 계산 결과가 바뀌거나, 계산 함수를 테스트하기 어려운 문제를 만든다.

이 프로젝트에서는 app.py를 화면 조립과 상태 관리에 사용하고, 계산 기능을 src 아래의 모듈로 분리했다.

학습할 핵심:

1) UI 함수는 입력을 수집하고 결과를 표시하는 역할만 맡는다.
2) 계산 함수는 DataFrame과 일반 값을 입력받아 결과를 반환한다.
3) 계산 함수 내부에서 Streamlit 세션이나 위젯에 접근하지 않는다.
4) 네트워크 요청, 시간 계산과 문자열 정제도 각각 별도 모듈로 분리한다.

이렇게 분리하면 동일 입력에 대한 결과를 UI 없이 테스트할 수 있다.
또한 Streamlit 이외의 웹 프레임워크로 교체하더라도 핵심 계산 모듈은 재사용할 수 있다.

관련 구조:

- app.py: 화면과 사용자 입력
- src/scoring.py: 계산과 순위
- src/evidence_scoring.py: 추가 근거 처리
- src/mobility.py: 외부 이동 API
- src/operating_hours.py: 시간표 상태 계산
- src/geolocation.py: 브라우저 위치정보
- src/chatbot.py: 대화 요청과 응답 계층

3. 데이터 파이프라인: raw와 processed 분리
======================================================================

데이터 프로젝트에서는 원천 파일을 직접 수정하면 재현성과 추적성이 사라진다.
따라서 원천 데이터와 실행 데이터를 분리하는 방식이 중요하다.

적용한 구조:

- data/raw: 원본 CSV, 엑셀, 수집 응답과 증거
- data/processed: 앱이 직접 읽는 정제 CSV
- scripts: 원본을 정제 결과로 변환하는 절차
- data/source_notes.md: 기준일, 출처와 처리 한계

학습할 핵심:

1) 원천 파일은 수정하지 않고 보존한다.
2) 컬럼명, 자료형, 좌표, 범주값은 processed 단계에서 통일한다.
3) 여러 데이터셋은 이름이 아니라 안정적인 식별자로 연결한다.
4) 데이터 생성과 데이터 검증을 별도 단계로 둔다.
5) 앱은 raw가 아니라 검증된 processed 데이터만 읽는다.

이 프로젝트에서는 facility_id를 공통 식별자로 사용했다.
시설 기본정보, 운영시간, 경로와 추가 입력을 facility_id로 결합함으로써 이름 표기 차이로 인한 연결 오류를 줄였다.

4. 데이터 검증을 별도 프로그램으로 만드는 이유
======================================================================

CSV 파일이 열리는 것과 데이터가 올바른 것은 다르다.
컬럼이 존재해도 ID 중복, 범위 오류, 잘못된 범주값과 연결 누락이 있을 수 있다.

검증 스크립트에서 확인한 항목:

- 필수 컬럼 존재 여부
- facility_id의 유일성
- 서로 다른 파일 사이의 ID 집합 일치
- 위도·경도 범위
- 음수가 될 수 없는 수치
- yes, no, unknown과 같은 범주값
- 경로 데이터의 예상 행 수
- 병원과 약국 분류값
- 보강 데이터와 기본 시설의 연결 상태

학습할 핵심은 앱 내부에서 오류가 발생한 후 원인을 찾는 것이 아니라, 앱 실행 전에 데이터 계약을 검사하는 것이다.
이 방식은 데이터 파일 교체 시 발생하는 문제를 가장 빠르게 발견한다.

5. 결정적인 계산과 순위 산정
======================================================================

추천이나 점수 계산은 같은 입력에서 항상 같은 결과를 반환해야 테스트와 설명이 가능하다.
이를 결정성이라고 한다.

결정성을 위해 적용한 원칙:

- 계산 함수는 현재 세션이나 화면 상태를 직접 읽지 않는다.
- 필요한 값은 모두 함수 인자로 전달한다.
- 반올림 전 원점수와 화면 표시 점수를 분리한다.
- 순위는 원점수로 결정한다.
- 동점일 때 적용할 보조 정렬 기준을 고정한다.
- 결측값의 기본 처리 규칙을 명시한다.

현재 계산은 다섯 구성 요소를 별도 값으로 유지한 뒤 가중합한다.
각 구성 요소를 분리하면 최종 점수만 저장하는 것보다 디버깅과 회귀 테스트가 쉬워진다.

원점수와 표시 점수를 분리해야 하는 이유:

두 결과가 화면에서 모두 70.1로 보여도 실제 원점수는 다를 수 있다.
표시 점수만으로 정렬하면 반올림 때문에 원래 순서가 뒤바뀔 수 있다.
따라서 정렬은 반올림 전 값을 사용하고, 화면에서만 소수점 자릿수를 제한한다.

6. 결측값을 중립적으로 처리하는 설계
======================================================================

실무 데이터에는 확인하지 못한 값이 많다.
unknown을 false로 바꾸면 확인하지 못한 상태가 부정적인 사실로 왜곡된다.
반대로 기본값을 true로 두면 확인되지 않은 시설이 과대평가된다.

적용한 구분:

- yes: 확인된 긍정 상태
- no: 확인된 부정 상태
- unknown: 확인하지 못한 상태

unknown은 점수 변화 없이 중립 처리했다.
확인된 데이터만 가점 또는 감점에 사용했다.

학습할 핵심:

1) 결측과 부정은 다른 상태다.
2) 결측값 처리 규칙은 계산식보다 먼저 결정해야 한다.
3) 데이터 신뢰도와 대상의 품질을 같은 점수로 취급하면 안 된다.
4) 출처와 수집 상태는 별도의 메타데이터로 유지해야 한다.

======================================================================
7. 중복 계산을 막는 방법
======================================================================

여러 데이터셋을 결합하면 같은 현상이 서로 다른 컬럼에 반복될 수 있다.
예를 들어 기존 경로 데이터와 새로운 보행 관측 데이터를 모두 이동 점수에 더하면 같은 이동 부담이 두 번 반영된다.

이를 방지하기 위해 데이터의 역할을 분리했다.

- 실제 출발지별 저장 경로: 경로 점수 계산
- 추가 보행 관측 수: 데이터 근거 수준 계산

학습할 핵심은 데이터셋 단위가 아니라 의미 단위로 변수의 역할을 정하는 것이다.
새로운 데이터가 추가될 때는 기존 계산 항목과 의미가 겹치는지 먼저 확인해야 한다.

중복 계산 검토 질문:

- 새 필드가 기존 필드와 같은 현상을 측정하는가?
- 최종 점수의 두 구성 요소에 동시에 들어가는가?
- 하나는 계산값, 다른 하나는 신뢰도나 설명용으로 사용할 수 있는가?
- 동일 현상을 두 번 반영했을 때 순위 변화가 과도해지지 않는가?

8. Streamlit의 실행 모델
======================================================================

Streamlit은 위젯 값이 바뀔 때 app.py를 위에서 아래로 다시 실행한다.
일반적인 웹 서버의 요청·응답 구조와 다르기 때문에 이 특성을 이해해야 한다.

주요 학습 요소:

- st.session_state: 재실행 사이에 유지할 사용자 상태
- st.cache_data: 동일한 데이터 로딩·계산 결과 재사용
- st.spinner: 시간이 걸리는 작업의 진행 상태
- st.error, st.warning, st.info: 실패와 대체 상태 표시
- st.tabs, st.expander, st.columns: 한 화면의 정보량 분리

데이터 로딩에 캐시를 적용한 이유:

위젯을 한 번 조작할 때마다 CSV 전체를 다시 읽으면 불필요한 디스크 접근이 반복된다.
정적 CSV 로딩 함수에 st.cache_data를 적용하면 입력 파일이 바뀌기 전까지 결과를 재사용할 수 있다.

외부 API 캐시에 TTL을 둔 이유:

외부 이동 데이터는 영구 캐시하면 오래된 결과가 남고, 캐시하지 않으면 위젯 변경마다 호출량이 증가한다.
따라서 일정 시간만 재사용하는 TTL 캐시가 적합하다.

9. Streamlit 상태 설계
======================================================================

세션 상태에는 화면을 다시 그릴 때 필요한 최소 정보만 저장해야 한다.
큰 DataFrame이나 민감한 원본 값을 무조건 저장하면 메모리와 보안 문제가 생긴다.

적용한 상태 유형:

- 선택한 프리셋 인덱스
- 최근 사용자 선택값
- 브라우저에서 전달된 검증된 위치정보
- 최근 추천 결과의 요약
- 최근 챗봇 메시지 일부

최근 추천 결과는 챗봇이 참조할 수 있도록 요약 형태로 저장했다.
전체 DataFrame 대신 이름, 순위, 거리, 이동시간과 필요한 정보만 저장해 결합도를 낮췄다.

10. 브라우저 위치정보와 Python 연결
======================================================================

Python 서버는 브라우저의 현재 위치에 직접 접근할 수 없다.
브라우저 Geolocation API는 클라이언트 측 JavaScript에서 실행해야 한다.

처리 흐름:

1) Streamlit HTML 컴포넌트에서 위치 권한을 요청한다.
2) 브라우저가 위도, 경도와 정확도를 반환한다.
3) 반환값을 Streamlit 컴포넌트 값으로 전달한다.
4) Python에서 자료형과 좌표 범위를 검증한다.
5) 검증된 값만 계산 입력으로 사용한다.
6) 실패하면 저장된 기준 위치를 사용한다.

학습할 핵심:

- 브라우저 기능과 서버 기능의 실행 위치가 다르다.
- 클라이언트에서 전달된 값은 항상 서버에서 다시 검증해야 한다.
- 현재 위치 기능은 localhost 또는 HTTPS에서만 안정적으로 사용할 수 있다.
- 사용자 권한 거부는 오류가 아니라 정상적인 대체 경로로 처리해야 한다.

11. 외부 API 연동 구조
======================================================================

외부 API는 성공하는 경로만 구현하면 안 된다.
네트워크 지연, 호출 제한, 빈 결과, 응답 스키마 변경과 인증 실패가 발생할 수 있다.

적용한 계층:

1) 요청 함수
- URL과 파라미터 구성
- 제한시간 설정
- JSON 파싱
- 네트워크 예외를 애플리케이션 예외로 변환

2) 응답 변환 함수
- 외부 JSON을 내부 표준 구조로 변환
- 총시간, 요금, 환승과 도보 구간 분리
- 빈 경로 처리

3) UI 연결 함수
- 로딩 상태 표시
- 오류 메시지 표시
- 저장 데이터 기반 대체 결과 유지

학습할 핵심:

- 외부 응답 구조를 UI에서 직접 사용하지 않는다.
- 파서가 외부 구조를 내부 데이터 모델로 변환해야 한다.
- API 실패가 앱 전체 실패로 이어지지 않도록 선택 기능으로 분리한다.
- 제한시간과 캐시를 함께 사용해 응답성과 호출량을 제어한다.

12. 전체시간을 중복 없이 분해하는 방법
======================================================================

외부 이동 API의 총 소요시간에는 도보시간이 이미 포함될 수 있다.
총시간, 교통시간과 도보시간을 그대로 더하면 시간이 중복된다.

적용한 분해 원칙:

- 총 소요시간: API가 제공한 전체 시간
- 야외시간: 경로 내부 도보 구간 합
- 교통·대기시간: 총 소요시간에서 야외시간을 제외한 값

이 방식은 합계가 항상 전체 시간과 일치하게 만든다.
서로 겹치지 않는 항목으로 나누는 것은 계산뿐 아니라 화면의 인지 비용을 줄이는 데도 중요하다.

======================================================================
13. 시간표 데이터를 상태로 변환하는 방법
======================================================================

문자열 시간표를 그대로 화면에 표시하는 것과 현재 상태를 계산하는 것은 별도 작업이다.

필요한 처리:

- 요일 결정
- 시작·종료 시간 파싱
- 점심시간 범위 확인
- 정기 휴무 확인
- 시간표 미확인 상태 분리
- 현재 시간대 기준 상태 계산

학습할 핵심:

- 시간 계산에는 타임존이 필요하다.
- 정규 시간표와 실시간 접수 상태를 구분해야 한다.
- 파싱 실패를 영업 중으로 해석하면 안 된다.
- 정보가 없을 때 사용할 안내 우선순위를 정해야 한다.

======================================================================
14. 외부 지도 검색 실패를 줄이는 문자열 정제
======================================================================

지도 검색 URL에 지나치게 상세한 주소를 전달하면 일부 서비스에서 검색 결과가 나오지 않을 수 있다.
이를 해결하기 위해 검색용 문자열을 별도로 만들었다.

적용한 처리:

- 기관명 유지
- 시·구·동 수준의 행정구역 유지
- 상세 번지와 불필요한 건물 세부정보 제거
- URL 인코딩 적용

학습할 핵심은 저장용 주소와 검색용 주소를 같은 문자열로 사용하지 않는 것이다.
데이터의 목적에 따라 표시용, 검색용과 계산용 표현을 분리할 수 있다.

======================================================================
15. 규칙 기반 응답과 외부 AI 결합
======================================================================

챗봇 기능은 모든 질문을 외부 모델에 보내지 않고 두 단계로 구성했다.

1단계: 로컬 규칙 기반 처리
- 시설명 검색
- 저장 운영정보 조회
- 최근 결과의 거리·이동정보 조회
- 지역 집계 조회
- 응급 키워드 검사

2단계: 선택적 외부 모델 처리
- API 키가 있을 때만 사용
- 구조화된 서비스 컨텍스트 전달
- 대화 이력 길이 제한
- 응답 저장 비활성화
- 요청 실패 시 로컬 응답으로 대체

학습할 핵심:

- 정확한 데이터 조회는 규칙 기반 경로가 더 안정적이다.
- 자연어 설명만 외부 모델에 맡길 수 있다.
- 안전 분기는 모델 호출 전에 실행해야 한다.
- 민감한 좌표와 불필요한 원본 데이터는 모델 컨텍스트에서 제거한다.
- 외부 모델 없이도 최소 기능이 동작해야 한다.

======================================================================
16. 테스트 전략
======================================================================

현재 테스트는 43개이며 다음 계층으로 구성된다.

1) 단위 테스트
- 거리 계산
- 시간 표시
- 환경 상태 변환
- 질환과 진료과 연결
- 가중합
- 운영시간 파싱
- 외부 API 응답 변환
- 주소 축약
- 좌표 검증
- unknown 처리

2) 추천 결과 테스트
- 같은 입력의 결과 결정성
- 거리 변화에 따른 점수 차이
- 조건 변화에 따른 순위 변화
- 동점 정렬
- 결과 구성 요소와 추천 이유 존재 여부

3) 앱 스모크 테스트
- 주요 페이지 로딩
- 기본 추천 화면
- 선택값 변경
- 결과 카드의 중복 제거
- 현재 위치 대체 흐름

4) 릴리스 교차 검증
- 대표 입력의 1순위와 점수 고정
- 가중합 수동 계산과 결과 일치
- 데이터 집계값과 보고 값 일치

학습할 핵심:

- UI 테스트만으로 계산 정확성을 보장할 수 없다.
- 계산 함수의 단위 테스트와 앱 스모크 테스트를 분리해야 한다.
- 대표 결과를 고정하면 의도하지 않은 회귀를 빠르게 찾을 수 있다.
- 데이터가 변경되면 고정 결과를 무조건 수정하지 말고 변화 원인을 먼저 확인해야 한다.

======================================================================
17. 오류를 발견한 순서와 학습 포인트
======================================================================

점수가 동일하게 보이는 문제
- 표시 점수 반올림과 구성 요소 차이를 분리해서 확인해야 한다.
- 원점수를 유지하고 각 구성 요소를 화면과 테스트에서 확인하도록 개선했다.

정보가 반복되는 문제
- 같은 이동시간을 카드, 문장과 상세 설명에서 반복하면 읽기 비용이 커진다.
- 수치, 근거와 설명의 역할을 분리하고 중복 문장을 제거했다.

상세주소 지도 검색 실패
- 저장 데이터가 정확해도 외부 검색 서비스의 질의 형식과 맞지 않을 수 있다.
- 검색 목적에 맞는 별도 정제 함수가 필요하다.

현재 위치가 불명확한 문제
- 좌표 계산만 구현하고 지도에서 시각적으로 구분하지 않으면 사용자가 확인하기 어렵다.
- 출발점 마커, 시설 순위, 연결선과 정확도 정보를 함께 표시했다.

외부 API가 없을 때 기능 중단 문제
- 선택 기능과 필수 기능을 분리해야 한다.
- API 키가 없거나 요청이 실패해도 저장 데이터 경로가 유지되도록 구성했다.

신규 데이터 이중 반영 위험
- 새 데이터가 추가되면 기존 변수와 의미 중복을 확인해야 한다.
- 보행 관측은 경로 점수가 아니라 근거 수준으로 분리했다.

18. 재현 가능한 실행환경 만들기
======================================================================

다른 컴퓨터에서 실행하려면 소스 코드만 전달해서는 안 된다.
실행에 필요한 데이터, 의존성 명세와 설정 예제가 함께 있어야 한다.

필수 구성:

- app.py
- src 디렉터리
- data/processed 디렉터리
- requirements.txt
- 빈 secrets.toml.example
- 실행 가이드

재현 절차:

1) Python 버전 확인
2) 가상환경 생성
3) 가상환경 활성화
4) requirements 설치
5) 데이터 파일 존재 확인
6) Streamlit 실행

학습할 핵심:

- 가상환경은 프로젝트별 의존성 충돌을 막는다.
- requirements.txt는 최소한의 재현 명세다.
- 실제 API 키는 배포물에 포함하면 안 된다.
- ZIP 생성 후 파일이 존재하는지만 보지 말고 다시 열어 내부 엔트리를 검사해야 한다.

19. 현재 구조에서 추가로 학습할 기술
======================================================================

의존성 고정
- 버전 범위만 있는 requirements.txt에서 lock 파일 기반 설치로 발전시킬 수 있다.

CI 자동화
- 데이터 검증과 43개 테스트를 GitHub Actions 같은 CI에서 자동 실행할 수 있다.

스키마 관리
- CSV 컬럼 계약을 JSON Schema, Pandera 또는 Pydantic 모델로 명시할 수 있다.

관측 가능성
- API 요청시간, 캐시 적중률, 실패 코드와 대체 경로 사용 횟수를 로그로 남길 수 있다.

부하 테스트
- Streamlit 다중 세션에서 메모리 사용량과 외부 API 호출량을 측정할 수 있다.

접근성 테스트
- 키보드 탐색, 색 대비, 화면낭독기와 포커스 순서를 자동 검사할 수 있다.

계산 버전 관리
- 결과에 scoring_version을 기록해 계산 변경 전후를 비교할 수 있다.

20. 학습 확인 질문
======================================================================

1) UI 함수와 계산 함수를 분리하면 어떤 테스트가 쉬워지는가?
2) raw 데이터와 processed 데이터를 분리하지 않으면 어떤 문제가 발생하는가?
3) unknown을 false로 처리하면 데이터 해석이 어떻게 왜곡되는가?
4) 표시 점수와 정렬용 원점수를 분리해야 하는 이유는 무엇인가?
5) 외부 API 응답을 UI에서 직접 사용하면 어떤 결합 문제가 생기는가?
6) 총시간과 도보시간을 동시에 보여줄 때 중복 계산을 어떻게 방지할 수 있는가?
7) Streamlit에서 캐시와 session_state의 역할은 어떻게 다른가?
8) 브라우저 위치정보를 서버에서 다시 검증해야 하는 이유는 무엇인가?
9) 규칙 기반 응답과 외부 AI를 함께 사용하는 장점은 무엇인가?
10) 대표 결과 고정 테스트가 실패했을 때 가장 먼저 확인할 것은 무엇인가?

21. 학습용 실습 제안
======================================================================

실습 1
- 새로운 CSV 필드를 추가하고 validate_data.py에 스키마 검사를 추가한다.
- 잘못된 범주값을 넣어 검증 실패를 확인한다.

실습 2
- 한 구성 요소의 가중치를 변경한다.
- 전체 합이 1인지 검사하고 대표 결과가 어떻게 달라지는지 비교한다.

실습 3
- 외부 API 파서에 빈 응답, 필드 누락과 시간 초과 테스트를 추가한다.

실습 4
- Streamlit 캐시를 제거했을 때와 적용했을 때 CSV 로딩 횟수를 비교한다.

실습 5
- 현재 위치 권한 허용, 거부와 지원하지 않는 브라우저의 대체 흐름을 테스트한다.

실습 6
- 새로운 데이터의 의미가 기존 계산과 중복되는지 검토하고 계산값, 신뢰도 또는 설명용 중 하나로 역할을 분류한다.

실습 7
- 전체 테스트를 CI에서 실행하고 데이터 검증 실패 시 빌드가 중단되도록 구성한다.

22. 핵심 기술 학습 요약
======================================================================

- 데이터 앱은 UI, 계산, 외부 연동과 검증을 분리해야 유지보수와 테스트가 쉽다.
- 원천 데이터는 보존하고 실행 데이터는 재생성할 수 있어야 한다.
- 식별자와 스키마 검증이 데이터 결합의 기반이다.
- 결측, 부정과 확인된 긍정 상태를 구분해야 한다.
- 새 데이터 추가 시 의미 중복과 이중 계산을 검사해야 한다.
- Streamlit은 전체 재실행 모델이므로 캐시와 세션 상태 설계가 중요하다.
- 외부 API는 요청, 변환과 UI 계층을 분리하고 실패 대체 경로를 가져야 한다.
- 브라우저에서 전달된 값과 외부 응답은 서버에서 다시 검증해야 한다.
- 테스트는 단위, 앱, 데이터와 릴리스 결과 계층으로 나누는 것이 효과적이다.
- 실행 가능한 배포물에는 소스뿐 아니라 데이터, 의존성 명세, 설정 예제와 실행 문서가 필요하다.
